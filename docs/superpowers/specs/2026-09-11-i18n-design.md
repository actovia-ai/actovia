# Application i18n — Design

**Date:** 2026-09-11
**Status:** approved (brainstorming 2026-09-11)

---

## Context

Actovia ships English-only. Every user-facing string is a hardcoded literal —
JSX text, `placeholder` / `aria-label` / `title` props, ~73 `sileo` toast
call-sites in the renderer, and in the main process the native menu
(`menu.ts`, ~15 labels), the tray (`tray.ts`), `new Notification(...)` copy
(migrations, auto-updater), the chat `notice` SSE events, and ~133 `Error(...)`
throws whose messages reach the user via `ErrorCode` + `app-error.ts`.

CLAUDE.md already codifies "new user-facing strings default to English"; this
design turns that into "new user-facing strings are keys in `en/*.json`".

Scope is **application i18n only**. Out of scope: the language the LLM replies
in (the model already mirrors the user's prompt language), and the English
system prompts / tool descriptions the model reads (models perform best on
English instructions — these are not UI).

The library choice is **i18next + react-i18next** (see Decisions). It was
weighed against Lingui (compile-time, ~5 kB, but adds a macro + extract/compile
step to all three electron-vite targets and changes how every string is
authored) and Paraglide (best type-safety, plain-function output, but newest
and its runtime-locale-switch story in a long-lived Electron renderer is less
proven). i18next is the lowest-risk path for a large two-process migration with
a live-switch requirement, and its JSON catalogs are the friendliest artifact
for a 10-locale machine-translation pass and any future TMS (Crowdin / Lokalise
/ Tolgee all speak i18next JSON natively).

## Decisions (from brainstorming, 2026-09-11)

| Question        | Decision                                                                                                                                                                                                                                 |
| --------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Library         | **`i18next` + `react-i18next` + `i18next-resources-to-backend`.** No `i18next-icu` (native CLDR plurals + `Intl` formatting suffice), no language-detector plugin (locale is resolved in main from `app.getPreferredSystemLanguages()`). |
| Locale set (v1) | **11:** `en` (source/fallback), `zh-Hant-TW`, `zh-Hant-HK`, `ja`, `ko`, `fr`, `de`, `es`, `pt-BR`, `ru`, `it`. No RTL languages. **No Simplified Chinese** — bare `zh` / any `zh-Hans*` resolves to `en`.                                |
| Chinese split   | `zh-Hant-TW` and `zh-Hant-HK` are **separate catalogs** with genuinely different vocabulary (軟體/軟件, 網路/網絡, 預設值/預設). HK falls back to TW before English.                                                                     |
| Translations    | Claude **machine-translates all 10** non-English locales in one pass once `en` is frozen; each locale's `_status.json` marks it `source: "machine"`; humans review later per namespace.                                                  |
| Stored value    | `settings.language`: one of the 11 IDs **or `"auto"`**. **Default `"auto"`.** The Settings selector's default option is "Auto (detect from system)".                                                                                     |
| Detection       | `"auto"` → walk `app.getPreferredSystemLanguages()`, match each by exact ID → `lang-Script` → base `lang`; `zh-Hant` → `zh-Hant-TW`; unmatched → `en`. Re-resolved on every launch and on app focus while the stored value is `"auto"`.  |
| Switching       | **Live, no restart.** Renderer `changeLanguage()` + re-render; main updates its instance and rebuilds the menu + tray via IPC.                                                                                                           |
| No-flash boot   | Main resolves the effective locale after DB migrate, **before** `createWindow()`, and exposes it as `window.actovia.locale` (preload). i18next initializes synchronously from it.                                                        |
| Catalog format  | Namespaced JSON under `src/shared/i18n/locales/<locale>/<ns>.json`. Dot-nested, component-scoped keys. Plurals via CLDR suffix keys.                                                                                                     |
| Loading         | Renderer **lazy-loads** per locale (active + `en` only in memory) via `import.meta.glob`. Main **bundles all 11** (tiny surface, no download concern).                                                                                   |
| Errors          | `AppError` carries `{ code, params }`, not a baked string. Rendered to text at the edge: `getHttpErrorMessage` uses the renderer instance, `new Notification` uses main's. `errors.json` is loaded in both processes.                    |
| Rollout         | Phased: (1) infra, (2) one PR per namespace to extract strings, (3) one MT pass, (4) selector UI + live switch, (5) flip the hardcoded-string guard to `error`.                                                                          |

## Locales

### IDs and display names (`src/shared/i18n/locales.ts`)

| ID           | `nativeName`       | date-fns locale | Plural categories     |
| ------------ | ------------------ | --------------- | --------------------- |
| `en`         | English            | `enUS`          | one, other            |
| `zh-Hant-TW` | 繁體中文（台灣）   | `zhTW`          | other                 |
| `zh-Hant-HK` | 繁體中文（香港）   | `zhHK`          | other                 |
| `ja`         | 日本語             | `ja`            | other                 |
| `ko`         | 한국어             | `ko`            | other                 |
| `fr`         | Français           | `fr`            | one, many, other      |
| `de`         | Deutsch            | `de`            | one, other            |
| `es`         | Español            | `es`            | one, many, other      |
| `pt-BR`      | Português (Brasil) | `ptBR`          | one, many, other      |
| `ru`         | Русский            | `ru`            | one, few, many, other |
| `it`         | Italiano           | `it`            | one, many, other      |

`date-fns` ships `zhHK`; `zhTW` is the fallback for Traditional Chinese
relative-time strings if a `zhHK` gap surfaces.

### `resolveLocale(prefs: string[]): LocaleId`

```
for each pref in prefs (already in the user's OS priority order):
  normalize (BCP-47 case): "zh-hant-hk" → "zh-Hant-HK"
  if pref is one of the 11 IDs                     → return it
  if pref starts "zh-Hans" or pref === "zh"        → skip (→ eventually "en")
  if pref matches "<lang>-<Script>" of an ID       → return that ID
  if pref's base "<lang>" matches an ID's base     → return the first such ID
    (special-case: base "zh" with script "Hant" or region TW/HK handled above;
     bare "pt" → "pt-BR"; bare "en-GB" etc → "en")
return "en"
```

Pure function, no Electron import — unit-tested directly.

### Fallback chain (i18next `fallbackLng`)

```js
{
  'zh-Hant-HK': ['zh-Hant-TW', 'en'],
  default: ['en'],
}
```

`NAMESPACES` in `namespaces.ts` is the one list; the loader, the type
augmentation, and `i18n:check` all derive from it.

### Key conventions

- Dot-nested, component- or feature-scoped: `chat.composer.placeholder`,
  `common.action.save`, `settings.providers.chatModel.label`,
  `errors.CONFIG_MISSING_PROVIDER`.
- Interpolation: `{{name}}`, `{{count}}`. No positional args.
- Plurals: CLDR suffix keys — `settings.memory.itemCount_one` /
  `_other`, plus `_few` / `_many` in the locales whose rules need them.
  The MT tooling emits the correct set per target locale from the `en`
  `_one`/`_other` pair.
- Rich text (a string with an inline link or `<b>`): a single key with
  `<0>…</0>` placeholders, rendered by `<Trans>`.
- Never interpolate a translated fragment into another string — no
  "sentence Lego". One key per whole sentence.

### `_status.json`

```json
{
  "locale": "ja",
  "source": "machine",
  "generatedAt": "2026-09-11",
  "reviewedNamespaces": []
}
```

`pnpm i18n:status` prints, per locale: `source`, and `reviewed N/13`.
A human reviewer adds a namespace name to `reviewedNamespaces` when its
translations are checked. `_status.json` is ignored by the i18next loader
and by TMS import (it is not a `<ns>.json`).

## Shared engine — `createI18n`

```ts
// src/shared/i18n/index.ts
export function createI18n(lng: LocaleId, opts: { isRenderer: boolean }) {
  const instance = i18next.createInstance()
  const common = {
    lng,
    fallbackLng: FALLBACK_LNG,
    ns: NAMESPACES,
    defaultNS: 'common',
    interpolation: { escapeValue: false }, // React escapes; main has no HTML sink
    returnNull: false,
    returnEmptyString: false
  }
  if (opts.isRenderer) {
    instance
      .use(initReactI18next)
      .use(
        resourcesToBackend(
          (l: string, ns: string) => import(`./locales/${l}/${ns}.json`)
        )
      )
      .init({
        ...common,
        partialBundledLanguages: true,
        react: { useSuspense: false }
      })
  } else {
    instance.init({ ...common, resources: BUNDLED_RESOURCES }) // all 11, static import
  }
  return instance
}
```

- `BUNDLED_RESOURCES` (main only) is built from `import.meta.glob('./locales/**/*.json', { eager: true })` filtered to `<ns>.json`.
- `react: { useSuspense: false }` + `partialBundledLanguages: true` so the
  first render uses whatever is loaded (the active locale is pre-seeded — see
  boot) and missing namespaces resolve through `fallbackLng` until their
  chunk lands, rather than throwing to a Suspense boundary.
- Number / date formatters: register `i18next`'s built-in `Intl` formatters
  in `createI18n` so `{{n, number}}` and `{{d, datetime}}` work inside
  catalog strings, bound to the instance's `resolvedLanguage`.

## Renderer integration

### Boot (no flash)

1. Preload exposes `window.actovia.locale: LocaleId` (main resolved it before
   `createWindow`).
2. Each entry point (`main.tsx`, `sub-apps/searchbar`, `sub-apps/quick-chat`,
   `sub-apps/artifacts`) imports a singleton from
   `src/renderer/lib/i18n.ts` that calls `createI18n(window.actovia.locale,
   { isRenderer: true })` and **awaits the active locale's namespaces**
   (`i18n.loadNamespaces(NAMESPACES)`) before `createRoot(...).render(...)`.
   `en` fallback chunks load in the background.

### `<I18nProvider>` + `<LocaleBridge>`

`src/renderer/components/i18n-provider.tsx`, modelled on `theme-provider.tsx`:

```tsx
export function I18nProvider({ children }) {
  return (
    <I18nextProvider i18n={i18n}>
      <LocaleBridge />
      {children}
    </I18nextProvider>
  )
}
```

`LocaleBridge` (side-effect only, like `NativeThemeBridge`):

- computes the effective locale from `useSettings()`:
  `settings.language === 'auto' ? window.actovia.locale : settings.language`.
  The renderer never calls `resolveLocale` — main already did, and its
  result is in `window.actovia.locale`. (When `"auto"` and the OS language
  changes at runtime, main re-resolves on app focus and pushes the new id
  via `webContents.send('locale-changed', …)`, which a small hook in the
  bridge applies.)
- on change: `await i18n.changeLanguage(next)` (pulls the new locale's
  chunks), `document.documentElement.lang = next`,
  `document.documentElement.dir = 'ltr'` (fixed — no RTL in v1),
  and `setAppLocale(next)` over IPC so the main process follows.

### Usage

- `const { t } = useTranslation('chat')` → `t('composer.placeholder')`.
- Toasts: `sileo.error({ title: t('errors.somethingWrong'), description: … })`.
- Rich text: `<Trans ns="settings" i18nKey="memory.autoCaptureHint">…</Trans>`.
- Outside React (rare — e.g. `stream-manager.ts` toasts): import the
  `i18n` singleton and call `i18n.t('…')` directly.

### Formatting — `src/renderer/lib/format.ts`

```ts
export function useFormat() {
  const { i18n } = useTranslation()
  const dfLocale = DATE_FNS_LOCALE[i18n.resolvedLanguage as LocaleId]
  return useMemo(
    () => ({
      relativeTime: (d: Date) =>
        formatDistanceToNow(d, { addSuffix: true, locale: dfLocale }),
      dateTime: (d: Date, o?: Intl.DateTimeFormatOptions) =>
        new Intl.DateTimeFormat(i18n.resolvedLanguage, o).format(d),
      number: (n: number, o?: Intl.NumberFormatOptions) =>
        new Intl.NumberFormat(i18n.resolvedLanguage, o).format(n)
    }),
    [i18n.resolvedLanguage]
  )
}
```

Replaces the direct `date-fns` calls in `nav-histories.tsx`,
`discover-feed.tsx`, and ~8 other files. `DATE_FNS_LOCALE` lazy-imports the
`date-fns/locale` objects.

### Not translated

Model IDs, provider display names, code blocks, URLs, user-authored content
(chat text, memory entries, project names), raw log payloads in the Logger
tab (the tab chrome is translated; the JSONL rows are not).

## Main-process integration

- `src/main/lib/i18n.ts`: `mainI18n = createI18n(effectiveLocale, { isRenderer: false })`, created in `app.ts` right after `runMigrate()` and `getSettings()`, before window creation.
- `effectiveLocale` = `settings.language === 'auto' ? resolveLocale(app.getPreferredSystemLanguages()) : settings.language`.
- Exposed to preload via a `contextBridge` value (`window.actovia.locale`) computed in the preload from an IPC `get-app-locale` call _or_ injected as an `additionalArguments` string on the `webPreferences` (synchronous, preferred — no IPC race at boot).
- Consumers: `menu.ts` (`buildMenu()` takes no args, reads `mainI18n.t`), `tray.ts`, `auto-updater.ts` notifications, `migrate.ts` notification, `chat.ts` `notice` events, `model-util.ts` / `app-error.ts` error messages.
- `setAppLocale(locale)` IPC handler: `mainI18n.changeLanguage(locale)` → `Menu.setApplicationMenu(buildMenu())` → `refreshTray()`.
- App-focus listener: if `settings.language === 'auto'`, re-run `resolveLocale`; if changed, `setAppLocale` internally + tell the renderer (it also re-resolves on focus via SWR revalidation, so a `webContents.send('locale-changed', next)` keeps them in lockstep).

## Errors

- `AppError` (in `src/shared/errors/app-error.ts`) gains `params?: Record<string, string | number>` and `hasCustomMessage: boolean`; the constructor no longer requires a message string — `code` + `params` is the payload when no explicit message is given. `hasCustomMessage` is `true` whenever a caller passed an explicit message (shown verbatim, untranslated — real dynamic exception text isn't translatable) and `false` when the error is purely code-driven (translated via `code` + `params`).
- `errors.json`: one key per `ErrorCode` enum member, nested under a `code` object (`errors.code.<CODE>`) to keep it visually distinct from scaffold keys (`somethingWentWrong`) and the `http.*` fallback set — e.g. `"code": { "CONFIG_MISSING_PROVIDER": "No AI provider selected. Choose one in Settings → AI Providers." }`, with `{{param}}` where the current strings interpolate (`PROVIDER_API_KEY_LABELS` etc. become params).
- Rendering:
  - `POST /api/*` error handler serializes `{ code, message, params?, hasCustomMessage }` via `AppError.toJSON()`.
  - Renderer `getHttpErrorMessage(e, i18n?)`: if `e.hasCustomMessage` (or `i18n` wasn't passed), returns `e.message` verbatim; otherwise `i18n.t(\`errors:code.${e.code}\`, e.params)`— note the`:`namespace separator (i18next's default), not`.`— falling back to`errors:http.<status>`/`errors:http.unknown`if the code key doesn't exist.`toErrorI18n()`(in`http.ts`) adapts a real i18next instance to the shape this function expects.
  - Main `new Notification({ body: mainI18n.t(\`errors:code.${code}\`, params) })`(not yet wired to any call site — no main-process`Notification`is currently driven by an`ErrorCode`).
- HTTP-status-only failures (no matching `code` key): `errors:http.<status>` keys + `errors:http.unknown`.

## Settings UI

- New row in **General** settings (`generals.tsx`): "Language" — a
  `SettingsSelect` whose options are `[{ value: 'auto', label: t('settings.general.language.auto') }, ...LOCALE_IDS.map(id => ({ value: id, label: LOCALES[id].nativeName }))]`. Each option label is shown in its own language (native name), the "Auto" label in the current UI language.
- Selecting writes `providerConfig`-style through the existing autosave →
  `POST /api/settings` → `LocaleBridge` reacts.
- `TEST_IDS.settings.language` added for the e2e spec.

## Tooling

| Script                | Does                                                                                                                                                                                                                                     |
| --------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm i18n:check`     | (also a Vitest test) For each non-`en` locale: JSON parses; key set === `en` key set modulo locale plural forms; every `{{var}}` in an `en` value appears in the translation; no orphan namespaces/keys. Fails the gate on any mismatch. |
| `pnpm i18n:status`    | Prints the `_status.json` review board.                                                                                                                                                                                                  |
| `pnpm i18n:translate` | (phase 3, run once) Reads `en/`, writes all 10 locales via a Claude translation pass, sets `_status.json`. Idempotent per key — skips keys already in `reviewedNamespaces`.                                                              |

**Hardcoded-string guard** — `tests/unit/i18n/no-hardcoded-strings.test.ts`:
scans `src/renderer/**/*.tsx` (excluding `components/ui/**` shadcn primitives,
`sub-apps/artifacts/sandbox.tsx`) and the main-process user-facing file
allowlist for:

- JSX text nodes matching `/[A-Za-z]{3,}/` not inside `<Trans>` / `{t(…)}` / a
  `className`/`data-*`/`aria-*` that's an identifier;
- `sileo.*({ title: '…' | description: '…' })` string literals;
- `label: '…'` in `menu.ts` / `tray.ts`.

Allowlisted exceptions live in `tests/unit/i18n/allowlist.ts` with a reason
per entry. The check is `warn`-level (informational) through phases 1–4 and
flipped to `error` (gate-blocking) in phase 5.

## Testing

- **Unit:**
  - `resolveLocale()` — the full matching ladder, incl. `zh-Hans-CN → en`,
    `zh-Hant → zh-Hant-TW`, `zh-Hant-HK → zh-Hant-HK`, `pt → pt-BR`,
    `en-GB → en`, `[] → en`, `['xx','ja'] → ja`.
  - `i18n:check` parity test (the tooling, run as a spec).
  - `useFormat()` — a fixed date rendered in `en` / `ja` / `ru` / `de`;
    plural rendering for `ru` (`_few`/`_many`) and `ja` (`_other` only).
  - `createI18n` (renderer mode) — missing-namespace lookup falls through
    `fallbackLng` without throwing.
- **E2E** (`tests/e2e/i18n.spec.ts`): launch, open Settings → General, switch
  Language to 繁體中文（台灣）, assert (a) a known chrome string (`New chat` →
  `新增交談`) is translated, (b) `document.documentElement.lang === 'zh-Hant-TW'`,
  (c) no restart occurred. The electron fixture sets `settings.language = 'en'`
  for every other spec.
- **Gate:** `pnpm i18n:check` joins `format → lint → typecheck → test` in
  the husky pre-commit hook.

## Rollout

### Phase 1 — Infrastructure (one plan, one branch)

Deps; `src/shared/i18n/` with `locales.ts`, `namespaces.ts`, `index.ts`,
`types.d.ts`, and **scaffold** `en/*.json` (valid JSON, a handful of real keys
so types resolve, the rest filled in phase 2); `src/renderer/lib/i18n.ts` +
`src/main/lib/i18n.ts`; `<I18nProvider>` + `<LocaleBridge>` wired into all
four entry points; `window.actovia.locale` through preload; `settings.language`
column + migration + schema; `setAppLocale` IPC; `resolveLocale` +
`useFormat` + tests; `i18n:check` / `i18n:status` scripts. **No user-visible
change** — every existing literal still renders exactly as today. Ships green.

### Phase 2 — Extraction (one plan per namespace, ~13 branches)

Per namespace: move that domain's literals into `en/<ns>.json`, swap call
sites to `t()` / `<Trans>`, migrate its `date-fns` calls to `useFormat`,
update its tests. Reviewable in isolation. Order: `common` → `errors` →
`menu` → `chat` → `settings` → the rest.

### Phase 3 — Machine translation (one plan, one branch)

`en` is frozen. `pnpm i18n:translate` generates all 10 locales × 13
namespaces; `_status.json` set to `source: "machine"`. JSON-only diff. `i18n:check` goes green for all locales.

### Phase 4 — Selector + live switch (one plan)

The General → Language row; `LocaleBridge` live `changeLanguage`; main menu /
tray rebuild on `setAppLocale`; app-focus re-resolve for `"auto"`; the e2e
spec.

### Phase 5 — Guard (one plan)

Flip `no-hardcoded-strings` to `error`, clear the allowlist to its permanent
minimum, document the "add a key, don't hardcode" rule in CLAUDE.md.
