# i18n Phase 2 — `menu` Namespace Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Extract every hardcoded, custom (non-`role`) label in the native macOS/Windows menu bar and the system tray's context menu, plus the two Philharmonic-domain OS `Notification` titles, into `src/shared/i18n/locales/en/menu.json`, wired through a new safe `mainT()` helper — with **zero visible change** to any currently-displayed English text.

**Architecture:** `menu.ts`'s menu template is currently built ONCE at module-import time (before `app.whenReady()`, before `initMainI18n()` even runs) — this plan converts it into a `buildMenu()` function evaluated at call time, so it reads `mainI18n`'s current state. `tray.ts`'s context menu is already rebuilt on every right-click (`buildContextMenu()`), so wiring it is nearly free. Since `mainI18n` can legitimately be `undefined` if `initMainI18n()` failed during boot (Phase 1's boot sequence tolerates this — it logs and continues rather than crashing), every one of this plan's call sites goes through a new `mainT(key, fallback, params?)` helper (added to `src/main/lib/i18n.ts`) that falls back to the same English text the catalog carries, with the same lightweight `{{param}}` substitution `AppError.interpolate` already uses in the `errors` namespace — so a rare init failure degrades to today's exact hardcoded behavior, never a crash or a raw `{{param}}` leak.

**Tech Stack:** Electron `Menu`/`Tray`, `i18next` (main-process instance, already wired via Phase 1 — no provider changes in this plan).

**Spec:** `docs/superpowers/specs/2026-09-11-i18n-design.md` (the `menu` namespace row, and the "Switching" decision — this plan explicitly does NOT build the live-rebuild-on-locale-change wiring the spec assigns to a later live-switch phase; see Global Constraints). Prior plans for context: `docs/superpowers/plans/2026-09-11-i18n-phase-2-errors-core.md` (the `AppError.interpolate` pattern this plan's `mainT()` mirrors) and `.../2026-09-11-i18n-phase-2-common.md` (established per-namespace extraction shape).

## Global Constraints

- **No visible change.** Every extracted label's `en` value is copied byte-identical from its current hardcoded literal.
- **Excluded from this pass (do not touch):**
  - `menu.ts`'s macOS app-name submenu `label: app.name` — not a hardcoded literal, mirrors Electron's own product-name API.
  - Every `role`-only menu item (`about`, `services`, `hide`, `quit`, `undo`, `copy`, `reload`, `minimize`, `help`, etc.) — Electron/the OS supplies its own localized default label; these have no custom `label:` override in this codebase and must not gain one.
  - Accelerator strings (`'CmdOrCtrl+L'`, `'CmdOrCtrl+F'`) — key combinations, not user-facing text.
  - `src/main/lib/db/migrate.ts:65-69`'s `new Notification(...)` — its `title`/`body` fire during `runMigrate()`, which the boot sequence (`src/main/index.ts`) runs **before** `initMainI18n()`; `mainI18n`/`mainT()` are unusable at that point by construction, not by omission. Stays hardcoded English, matching the `errors (core)` plan's identical, already-established ruling for this exact site.
  - `src/main/lib/auto-updater.ts`'s two error-message fallback literals (`'Unknown error'`, `'Check failed on startup'`) — these are IPC payload fields the renderer displays, not OS-level menu/tray/notification chrome; they belong to `errors`-namespace territory (already a completed phase) or a later general sweep, not this plan.
  - `src/main/lib/lock/lock-notifications.ts`'s `pushLockNotification` — dormant, zero callers anywhere in the repo; no literal strings exist to extract.
  - **Live rebuild on `set-app-locale`.** The design spec explicitly assigns "rebuild the menu + tray on a locale change" to a later live-switch phase, not this one (`src/main/lib/i18n.ts`'s `set-app-locale` handler already has a comment saying so). This plan only makes `buildMenu()`/`buildContextMenu()` read `mainI18n`'s CURRENT state at whatever point they're next called — it does not add any new call to `Menu.setApplicationMenu(...)` or a tray rebuild inside `set-app-locale`. Since the app always boots in one locale today (no live-switch UI exists yet), this is a genuine no-op behaviorally, not a partial feature.
- **`mainT()` usage convention (new in this plan):** `mainT(key, fallback, params?)` — `key` is the full `ns:key` form (e.g. `'menu:file'`, `'menu:notification.philharmonicGroupError'`) since main-process code has no per-file "default namespace" the way `useTranslation(ns)` gives the renderer; `fallback` is the exact same English text as `menu.json`'s value for that key (kept in the source file itself, not looked up, precisely so a `mainI18n`-unavailable path never needs i18next to produce correct English).
- **Pre-commit gate unchanged:** `pnpm format` → `pnpm lint` → `pnpm typecheck` → `pnpm i18n:check` → `pnpm test`. `--no-verify` only for the documented PGlite WASM teardown flake.
- **Follow existing patterns:** match each file's existing import-grouping style (`oxfmt` reorders automatically).

```ts
/**
 * Safely translates a main-process string, tolerating `mainI18n` being
 * unassigned — `initMainI18n()` can fail during boot (see its `.catch()` in
 * `index.ts`), and boot continues in English rather than crashing. `fallback`
 * must be the exact same English text as the catalog's value for `key`, so
 * the two paths render identically. When `mainI18n` isn't ready, a
 * lightweight `{{param}}` substitution (the same pattern `AppError.interpolate`
 * uses for the `errors` namespace) keeps interpolated content correct even
 * without i18next.
 */
export function mainT(
  key: string,
  fallback: string,
  params?: Record<string, string | number>
): string {
  if (mainI18n) return mainI18n.t(key, params)
  if (!params) return fallback
  return fallback.replace(/\{\{(\w+)\}\}/g, (match, k: string) =>
    k in params ? String(params[k]) : match
  )
}
```

```ts
import { ACTOVIA_WEBSITE } from '@shared/constants/external-urls'
import {
  app,
  BrowserWindow,
  Menu,
  MenuItemConstructorOptions,
  shell
} from 'electron'

import { mainT } from './i18n'
import { getLockManager } from './lock/lock-manager'
import { registerSearchMenu } from './window'

const isMac = process.platform === 'darwin'

function buildMenu(): MenuItemConstructorOptions[] {
  return [
    ...(isMac
      ? [
          {
            label: app.name,
            submenu: [
              { role: 'about' },
              { type: 'separator' },
              { role: 'services' },
              { type: 'separator' },
              { role: 'hide' },
              { role: 'hideOthers' },
              { role: 'unhide' },
              { type: 'separator' },
              { role: 'quit' }
            ]
          }
        ]
      : []),
    {
      label: mainT('menu:file', 'File'),
      submenu: [
        {
          label: mainT('menu:lockNow', 'Lock Now'),
          accelerator: 'CmdOrCtrl+L',
          click: () => getLockManager().lock('manual')
        },
        { type: 'separator' },
        isMac ? { role: 'close' } : { role: 'quit' }
      ]
    },
    {
      label: mainT('menu:edit', 'Edit'),
      submenu: [
        {
          label: mainT('menu:find', 'Find'),
          accelerator: 'CmdOrCtrl+F',
          click: () => {
            const mainWindow = BrowserWindow.getFocusedWindow()
            if (!mainWindow) return
            registerSearchMenu(mainWindow)
          }
        },
        { role: 'undo' },
        { role: 'redo' },
        { type: 'separator' },
        { role: 'cut' },
        { role: 'copy' },
        { role: 'paste' },
        ...(isMac
          ? [
              { role: 'pasteAndMatchStyle' },
              { role: 'delete' },
              { role: 'selectAll' },
              { type: 'separator' },
              {
                label: mainT('menu:speech', 'Speech'),
                submenu: [{ role: 'startSpeaking' }, { role: 'stopSpeaking' }]
              }
            ]
          : [{ role: 'delete' }, { type: 'separator' }, { role: 'selectAll' }])
      ]
    },
    {
      label: mainT('menu:view', 'View'),
      submenu: [
        { role: 'reload' },
        { role: 'forceReload' },
        { role: 'toggleDevTools' },
        { type: 'separator' },
        { role: 'resetZoom' },
        { role: 'zoomIn' },
        { role: 'zoomOut' },
        { type: 'separator' },
        { role: 'togglefullscreen' }
      ]
    },
    {
      label: mainT('menu:window', 'Window'),
      submenu: [
        { role: 'minimize' },
        { role: 'zoom' },
        ...(isMac
          ? [
              { type: 'separator' },
              { role: 'front' },
              { type: 'separator' },
              { role: 'window' }
            ]
          : [{ role: 'close' }])
      ]
    },
    {
      role: 'help',
      submenu: [
        {
          label: mainT('menu:learnMore', 'Learn More'),
          click: async () => {
            await shell.openExternal(ACTOVIA_WEBSITE)
          }
        }
      ]
    }
  ] as MenuItemConstructorOptions[]
}

export function setupMenu() {
  Menu.setApplicationMenu(Menu.buildFromTemplate(buildMenu()))
}
```

(This is a mechanical conversion: the old module-scope `const menuTemplate = [...]` becomes the return value of a new `function buildMenu()`, called from `setupMenu()` at the exact same point `setupMenu()` was already called from — `src/main/index.ts:95` — so boot behavior and timing are unchanged. The only content changes are the 8 `label:` values switching from string literals to `mainT(...)` calls.)
